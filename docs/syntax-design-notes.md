# Bolide 语法优化笔记

> 基于 Bolide `0.13.1` 的 README 与教程做的设计审视。**这是建设性建议,不是缺陷清单。**
> 贯穿全篇的判断只有一句:**机制大多借得不错,但还没"收口"——当前阶段收敛比加特性更能提升语言质感。**
>
> 标注 `待确认` 的条目依赖实现细节(如是否支持表达式语句、`_` 丢弃符),作者可直接验证。

---

## 优先级总览

| # | 主题 | 一句话问题 | 优先级 | 破坏性 |
|---|------|-----------|--------|--------|
| 1 | 类型修饰 / 所有权语法 | 三套风格、修饰位置散落,缺统一心智模型 | 中 | 是 |
| 2 | 布尔语义 | 有 `bool` 却让一批方法返回 `0/1` | 中 | 是 |
| 3 | 通道收发 | 收发不对称、接收强制 `=`、符号与方法风格割裂 | 高 | 视方案 |
| 4 | 错误处理 | `enum/match` 与 `try/catch` 双轨,异常限同函数内 | 高 | 否(增强) |
| 5 | 并发原语 | 概念面铺得广、每个偏薄 | 中 | 否(收敛) |
| 6 | 词法歧义 / 字面量 | 上下文关键字 `all` 冲突、后缀大小写过宽 | 低 | 是 |

## 1. 统一类型修饰与所有权语法

**现状** —— 同样是"给类型加修饰",存在三套不一致的写法,且所有权关键字散落在三个位置:

```bolide
let xs: list<int>            // 尖括号
let w:  weak Node            // 前缀裸名(不是 weak<Node>)
let f:  func(int) -> int     // 括号 + 箭头

fn take(owned v: list<int>)          // owned 在参数前
fn bump(ref n: int)                  // ref 在参数前
fn first(ref xs: list<str>) -> str from xs   // from 在签名末尾
```

学习者很难形成一个统一规则:容器用 `<>`,弱引用却不用;owned/ref 在前、from 在后。

**建议** —— 选一条主线并贯彻:

- 类型层修饰统一为尖括号:`weak<Node>` / `unowned<Node>`,和 `list<T>` 对齐;
- 所有权修饰统一收到同一处(建议都做参数/返回的前缀修饰符),让 `from` 也有一个对称写法;
- 在文档里给出一张"修饰符出现位置"总表,作为语言的硬约定。

> 收益:把"散落的特性"变成"一条可推导的规则",显著降低记忆成本。

## 2. 布尔语义统一

**现状** —— 语言有 `true`/`false`,但一批判定方法返回整数:

```bolide
print(s.contains("World"));  // 1
print(nums.is_empty());      // 0 / 1
print(s.starts_with("He"));  // 1
```

这是 C 的遗留味,和"现代 / Python 风格"的定位直接冲突,也让 `if s.contains(...)` 的读者要确认"这到底是 bool 还是 int"。

**建议** —— 所有 `contains/starts_with/ends_with/is_empty/...` 一律返回 `bool`。
若出于兼容暂不能改,至少在文档中显式声明返回类型,并规划一个迁移版本。

```bolide
// 目标
print(s.contains("World"));  // true
```

## 3. 通道收发:对称性 + 风格一致 + 可丢弃

这是 trade-off 最集中、也最值得打磨的一处。**现状**有三个叠加的小别扭:

```bolide
c <- 42;            // 发送:独立语句,OK
let v = <- ch;      // 接收:必须挂在 = 右侧
// <- ch;           // 纯接收/同步:疑似不被允许   ← 待确认
```

1. **收发不对称**:发送能独立成句,接收必须绑定到 `=`。对偶操作被给了不对等的语法待遇。
2. **缺纯同步**:用 channel 当"信号"(`<- done` = 阻塞等待)是核心并发惯用法;若强制 `=` 又没有 `_` 丢弃符,就只能造废变量 `let _ignore = <- done;`。
3. **风格割裂**:全语言是方法风格(`s.upper()` / `nums.push()` / `db.all()`),通道却突然用裸符号 `<-`。

**建议(任选一致的一条)**:

- **方案 A — 倒向方法风格(与语言整体最自洽)**

  ```bolide
  ch.send(42);
  let v = ch.recv();
  ch.recv();          // 纯同步,丢弃值自然合法
  ```
  代价:`select` 分支里 `x <- ch1 =>` 的"模式感"会变弱。

- **方案 B — 保留 `<-`,但补齐对称性与丢弃**

  ```bolide
  c <- 42;
  let v = <- ch;
  <- ch;              // 允许独立成句(纯同步)
  let _ = <- ch;      // 引入 _ 丢弃符,明确"接收但不要值"
  ```

无论哪条,关键是**收发两端语法范畴对齐**,并给"接收但不消费"一个干净写法。

> 检验现状只需两行:`<- ch;` 是否能独立成句、`let _ = <- ch;` 是否接受 `_`。

## 4. 错误处理:双轨收敛 + 异常跨函数

**现状** —— 两套机制并存,且异常半成品:

```bolide
// 轨道一:ADT 风格(Result/Option 思路)
match parse(x) { OptionInt.Some(v) => ..., OptionInt.None() => ... }

// 轨道二:Java 风格异常
try { throw Error("boom"); } catch (e: Error) { ... } finally { ... }
```

两个限制最伤:

- 异常**当前只能在同一函数内**捕获 → 它实际上更接近"局部跳转语法糖",真正的跨层错误仍得靠返回值;
- `throw` 可抛任意类型,`catch (e: int)` 这类按基础类型匹配的写法很脆弱。

**建议**:

- 明确两套机制的**分工边界**并写进文档:可恢复错误走返回值 / `Option` / `Result`;异常只用于"非预期、需跨层中止"的情形;
- 把"跨函数栈展开"提上日程——没有它,异常这套语法的价值发挥不出来;
- 约束 `throw` 的目标类型(建议收敛到 `Error` 及其子类),让 `catch` 的匹配语义稳定、可读。

## 5. 并发原语:概念瘦身

**现状** —— 并发是野心最大的部分,但原语偏多、单个偏薄:

```
async 冷 Future + spawn 真线程     // 两套执行模型
await / join                      // 两个等待原语
spawn all / spawn select / select / pool / channel
channel 仅支持值类型              // 能力缺口
```

概念面广会让使用者难以建立"什么时候用哪个"的直觉。

**建议**:

- 梳理一张**决策表**:同步等待用什么、并行汇聚用什么、竞态取首个用什么,减少同义原语(如 `await` 与 `join` 能否归一);
- 优先补齐能力缺口(如 channel 传对象的 Arc 方案)而非新增语法面;
- 把"薄"的特性做厚一两个,胜过再铺一层新关键字。

## 6. 词法歧义与字面量

**现状**:

```bolide
spawn all { ... }        // all 是上下文关键字
let xs = db.all("posts") // all 又是方法名 → 解析冲突(README 已自承)

let x = <- ch;           // <- 与 < - 仅一空格之差(maximal-munch 才能区分)

let a = 19.99d;          // 后缀 d / D 都接受,b / B 都接受
```

**建议**:

- 上下文关键字要么改名、要么用更强的语境界定,避免和成员调用(`.all(...)`)抢词——README 里"应改编译器而非改 API"的注脚,本质是语法没留够余量的信号;
- 字面量后缀**收敛到单一大小写**(建议统一小写 `b`/`d`),宽松到团队内不一致就得不偿失;
- `<-` 的词法歧义可在文档里显式说明规则,或在格式化器中强制 `a <- b` 两侧留空格。

---

## 建议推进顺序

1. **先收口,后加料。** 优先做 #4(异常分工 + 跨函数)和 #3(通道收发对称),这两处直接影响"能不能正确写并发/错误处理"。
2. **再做一致性。** #1 类型修饰、#2 布尔、#6 词法,属于"质感"层面,破坏性变更尽量集中到同一个版本一次性切。
3. **能力补齐穿插其中。** #5 的 channel 传对象等缺口,按并发路线图推进。

---

*一句话收尾:Bolide 没有犯方向性错误,缺的是一条贯穿全局的一致性原则。把"借来的零件"按自己的基调重铸一遍,它会从"能用且好上手"走向"耐看"。*
